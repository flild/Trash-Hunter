# Архитектура и правила реализации

Статус: технический проект v0.1. Это предложение для D-070, не готовые классы
и не разрешение на код. Текущее окружение и команды — [DEVELOPMENT](DEVELOPMENT.md).

## Принцип

Простая одиночная игра: чистые правила состояния там, где важны учёт и проверки;
Unity-компоненты для ввода, сцены, физики и отображения. Размер проекта подрузумевает использование ECS, DI-контейнера, глобальной шины событий, сетевого слоя или микросервисов, если это требуется и сделает проект лучше, но без overhead. Использовать только необходимое
Новые зависимости добавляются под конкретную подтверждённую задачу.

## Предлагаемые границы

| Область                 | Владеет                                               |
| ----------------------- | ----------------------------------------------------- |
| Input / Player          | Команды движения и взаимодействия, камера             |
| Interaction             | Выбор доступного объекта, взять/осмотреть/вернуть     |
| Items                   | Определения, экземпляры, состояния и принадлежность   |
| Inventory               | Вместимость и атомарный перенос экземпляров           |
| Expedition              | ID, seed, состав, начало и завершение вылазки         |
| Trade                   | Предложение и подтверждение продажи                   |
| Progression — позже     | Знания, контакты и условия открытий                   |
| Needs / Effects — позже | Потребности и ограниченные временные эффекты          |
| Story — позже           | Устойчивые факты и условия этапов                     |
| UI / Audio              | Показывает состояние и отправляет команды             |
| Save — позже            | Снимок подтверждённого состояния и его восстановление |

Это логические границы, а не требование создать по менеджеру, интерфейсу и сборке
для каждой строки. В прототипе использовать только необходимые части до Trade.
Прямые сериализованные ссылки и обычные C# вызовы предпочтительнее скрытого
поиска объектов по сцене и статических глобальных сервисов.

## Данные и владение

- ItemDefinition как ScriptableObject: стабильный ID и неизменяемые правила типа,
  prefab, признаки, объём и параметры оценки. Не записывать прогресс в этот ассет.
- ItemInstance как обычные данные: уникальный ID, definitionId, состояние,
  найденные признаки и одна принадлежность. Unity-представление ссылается на ID.
- PlayerKnowledge отдельно: известные модели, история продаж и навыки.
- ExpeditionState: ID, seed, список экземпляров и разрешённое состояние вылазки.
- GameState: кошелёк, домашние вещи, вылазка; позже контакты/сюжет/потребности.

Один владелец изменяемого состояния. UI читает снимок и вызывает действие владельца;
не редактирует список инвентаря или деньги самостоятельно. Удаление визуального
объекта не означает продажу. Состояние обновляется до запуска необратимого
визуального результата, с понятным отказом при невозможном переходе.

## Инварианты

1. InstanceId присутствует только в одном месте: мир, рука, сумка, дом или
   терминальное состояние Sold/Consumed/Discarded. Размер сумки не превышается.
2. Цена и скрытое состояние не перебрасываются при осмотре, повторном входе
   в контейнер или запросе предложения.
3. Новое заполнение создаётся только при разрешённом начале новой вылазки.
4. Одна продажа/порция/награда применяется один раз. Проверить принадлежность,
   затем в одной операции изменить её и баланс/эффект.
5. Неудавшаяся операция не должна оставлять половину изменения: нет денег
   без списания вещи и списания без денег.
6. Сюжетные факты не зависят от существования визуального объекта в сцене.
7. Настройка интенсивности эффектов меняет представление, а не истинные данные.

Это требования к будущим проверкам, не заявление об уже существующей защите.

## Физика и сцены 

Кинематический или CharacterController-подход игрока выбрать в D-070 после правил
входа/лазания. Хлам — Rigidbody с простыми коллайдерами и заранее проверенными
точками укладки. Осмотр может временно переводить конкретный объект в управляемое
состояние; его исходные параметры нужно восстановить при возврате.

Масса, сон, слои коллизий и скорость перемещения предмета настраиваются на малом
наборе. Не обещать физическую устойчивость по диаграмме. Вынесенную/провалившуюся
вещь можно безопасно вернуть в доступную точку с тем же ID, не создавать замену.
Правило такого восстановления утвердить при прототипе.

SetupCheck и SampleScene сохранить. Будущая сцена прототипа создаётся отдельно
через Editor после разрешения. Фактическую структуру папок сейчас не расширяем.

Предлагаемая структура будущего игрового кода:

```text
Assets/TrashHunter/
  Runtime/       # подпапки по реально появившимся областям
  Editor/        # инструменты разработки
  Tests/         # EditMode и PlayMode по необходимости
  Content/       # определения и prefab
  Scenes/        # игровые сцены
AgentScripts/    # внешние скрипты автоматизации Pipeline
docs/           # документация, вне импорта Unity
```

Не создавать пустые каталоги, десятки asmdef и интерфейсы-заглушки.
Разделение сборок вводить при реальной необходимости изоляции Editor/тестов.

## Сохранения — предложение, до реализации нужно выбрать Q-009

Предпочтение: версионированный снимок данных по стабильным ID; локальные настройки
отдельно от прохождения. Не использовать имена сценовых объектов и Unity
instanceID в качестве постоянных ID. Не хранить состояние игры в PlayerPrefs.

Вариант для обсуждения: автоматически сохранять подтверждённые операции дома,
начало вылазки и безопасный выход из активного поиска. Активная вылазка сохраняет
seed, фактические состояния/принадлежность экземпляров и нужные позиции.
При загрузке восстанавливать предметы в устойчивой конфигурации, без требования
побитового воспроизведения состояния PhysX.

Seed сам по себе недостаточен после перемещения и взятия вещей. Для случайного
содержимого сохранять результат генерации либо её версию вместе с данными.
Писать через временный файл и замену с резервной копией; повреждённый файл
не перезаписывать молча. Число слотов, ручное сохранение, формат, миграции и
поведение при аварийном завершении остаются открытыми.

Первый прототип может быть полностью в памяти с честно обозначенным сбросом
при завершении Play Mode. Это не считается реализованными сохранениями и
не проверяет устойчивость к перезапуску приложения.

## UI и код

Предложение P-006: uGUI для небольшого прототипа, потому что пакет уже установлен.
Сравнить с UI Toolkit при D-070 по реальным экранам. Не смешивать два runtime
фреймворка без причины. До UI-кода использовать официальный UI skill.

Namespace TrashHunter; классы/методы PascalCase, параметры/локальные переменные
camelCase; имена по назначению. Одна MonoBehaviour в одноимённом файле.
Тюнинг в данных/сериализованных полях, без разрозненных магических чисел.
Комментарии объясняют причину и ограничения; не повторяют строку кода.
Не добавлять широкую абстракцию или универсальный менеджер ради одной операции.

## Проверка будущего кода

EditMode: вместимость, отказ без частичного изменения, оценка, принадлежность,
повтор продажи/награды, сериализация и восстановление данных после появления Save.
PlayMode: взаимодействие и возврат предмета, границы вылазки, физическая доступность,
синхронизация UI и состояние при выходе. Визуальный комфорт и интерес проверяет
владелец вручную по сценарию PROTOTYPE.

Проверки чистых правил не доказывают физику, а Console без ошибок не доказывает UX.
Постоянные сохранения потребуют отдельной проверки закрытия/повторного запуска.
Никакие из этих игровых тестов в текущей сессии не выполнялись.
