# Trash-Hunter: инструкции для следующих сессий

## Текущий режим

Проект находится на этапе проектирования. Пользователь хочет сначала описать игру,
сюжет, правила разработки и архитектуру. До его прямого указания начать реализацию
работать только с документацией. Наличие плана прототипа не разрешает писать игровые
системы, создавать игровые сцены или устанавливать дополнительные пакеты.

## Начало сессии

1. Прочитать этот файл, [карту документов](docs/README.md),
   [состояние](docs/PROJECT_STATE.md) и [задание](docs/NEXT_SESSION.md).
2. Проверить Git status и относящиеся к задаче файлы. Отчёт не важнее реальных файлов.
3. Открывать далее только нужные документы и код, учитывая более локальные AGENTS.md.
4. Выбрать одну небольшую законченную задачу или тесно связанную группу.
   До изменений назвать результат и критерии готовности.

## Продуктовые решения

- Владелец проекта принимает продуктовые решения; агент предлагает и выполняет работу.
- Различать подтверждённые требования, предложения и открытые вопросы.
  Реестр: [DECISIONS.md](docs/DECISIONS.md). Молчание не означает утверждение.
- Исходное вложение задаёт требования; более поздние ответы пользователя их уточняют.
  Особенно: следующая сессия продолжает дизайн, а не начинает код из старого брифа.
- Некритичное неизвестное можно временно разрешить, явно записав предположение.
  Вопросы задавать небольшими тематическими группами; не выдавать анкету обо всей игре.
- Не добавлять функции ради потенциального будущего. Не менять утверждённое направление
  без причины и согласования изменения с владельцем.
- Точные бюджеты, сроки, длительность игры, число локаций и баланс пока не утверждены.

## Документы как память проекта

- Документы и отчёты на русском; пути и идентификаторы кода на английском. UTF-8.
- Вся документация в docs/, дизайн в docs/design/. Постоянные инструкции — здесь.
- У каждого правила одно основное место хранения. В других документах — ссылки.
- Новый документ создавать при самостоятельной необходимости, добавлять в карту.
- После работы обновлять PROJECT_STATE, затронутые документы, BACKLOG и краткий отчёт
  в docs/sessions/. Полностью переписывать NEXT_SESSION под актуальную следующую задачу.
- Незавершённое обозначать как частичный результат с конкретным остатком.
- В конце сообщить: что сделано; свежие проверки и непроверенное; что дальше;
  готовый короткий промпт нового чата, направляющий к документам репозитория.

## Unity и техническая работа

- Корень Git и Unity: F:\UnityProjects\Trash-Hunter. Подпапки Game нет.
- Сначала читать [DEVELOPMENT.md](docs/DEVELOPMENT.md). Окружение уже настроено.
  Не переустанавливать CLI/Pipeline, не создавать второй Unity-проект, не обновлять
  Editor/пакеты попутно. Версии проверять по текущим файлам, а не старому отчёту.
- Использовать официальный Unity-плагин, его unity-cli и unity-pipeline skills.
  Для Editor — Unity CLI/Pipeline с полным --project-path и маркировкой
  --caller plugin --skill unity-pipeline. Схемы команд сверять локально.
- Не менять сцены и сериализованные ассеты ручной генерацией YAML.
  Перемещение ассетов — через Editor, GUID и .meta сохранять.
- Скрипты автоматизации Pipeline хранить в AgentScripts/ вне Assets/.
  Runtime, Editor и тестовый код разделять; MonoBehaviour — отдельный одноимённый файл.
- Архитектурный черновик: [ARCHITECTURE.md](docs/ARCHITECTURE.md).
  Не строить инфраструктуру для ещё не утверждённых систем.
- До нового UI изучить существующие экраны и паттерны; перед UI-кодом прочитать
  официальный Unity UI skill. Выбор UI-фреймворка сейчас лишь предложение.

## Проверки и сохранность работы

- Не переписывать несвязанные системы и не удалять пользовательские изменения.
- Перед изменениями проверить status, перед фиксацией — staged и unstaged diff,
  добавлять только явные пути. Не выполнять reset/clean, не удалять Git/Gradle locks.
- Проверять соразмерно изменению: документацию — на ссылки, непротиворечивость,
  статус решений и diff; будущие игровые изменения — в подключённом Editor.
- Не заявлять, что сцена работает, по одному чтению исходников или status.
  Play Mode сам по себе не доказывает продвижение кадров или правильность механики.
- Не запускать и не останавливать пользовательскую Play-сессию без необходимости.
  Временно изменённые настройки Editor восстанавливать.
- Указывать отдельно свежие результаты, исторические проверки и ручную проверку.
  Для ручной проверки давать шаги и ожидаемый результат.
- Commit допустим для завершённой задачи в рамках запроса; push, публикация,
  выпуск/распространение билда — только по прямому указанию пользователя.
- Покупки не выполнять; бюджет на ассеты не предполагать. Перед использованием
  стороннего контента зафиксировать источник, лицензию и требуемую атрибуцию.
- Секреты, учётные данные, кеши и локальные логи не включать в Git.
